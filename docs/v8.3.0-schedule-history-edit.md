# v8.3.0 — Edit Original Start Date

## Context

Owner reported (via 2026-05-12 backup inspection) that their schedule shows `startDate: "2026-05-04"` even though they began the protocol on **2026-03-23**. They've ADJUSTed the schedule a few times and at some point either REMOVE-then-CREATE'd or hit a code path that reset the start date forward. As a result:

- The calendar overlay (white border = `schedule.days[]` member) only covers 5/4 → 5/20, so 3/23 → 5/3 logs look "unscheduled."
- The TODAY tab's "DAY X / TOTAL DAYS" strip reflects 17-day Phase-D block instead of the 51-day true journey.
- The radar's behavioral-scoring window anchors at 5/4 instead of 3/23.
- The export's default date range starts at 5/4.

The owner doesn't want a one-off data fix (hardcoding 3/23 would only help them). They want a **generic UI control** that lets any user edit the schedule's start date independently of the ADJUST math, with a clear "use only if start date was lost / changed by a bug / you want to backdate" label.

The fix must be safe — no duplicate fast/light days, no re-running adjustment math, no touching weight logs / dayLogs / food log / activity history, and an auto-backup before write.

---

## Scope

**One new feature:** "EDIT START DATE" button inside the MANAGE SCHEDULE modal that opens a sub-modal where the user can pick an earlier start date and confirm a start weight, after which `schedule.days[]` is extended backward and `schedule.startDate` / `schedule.startWeight` / `schedule.totalDays` / `schedule.exactDays` / `settings.startDate` are updated.

**Out of scope:**
- Forward-trim from start (already exists conceptually via END TODAY / REMOVE; out of scope here).
- Auto-detecting bad start dates and prompting (the owner wants explicit manual control, not auto-magic).
- Backfilling fast/light days on the extended range (user already has whatever fast/light data they recorded; we don't touch it).
- Recalculating target end date / kg-per-week projection (this is intentionally NOT what the feature does — owner asked specifically that target date stay where it is).
- Schema migration (no shape change to stored data).

### Validation rules (on APPLY)

1. New start date is a valid `YYYY-MM-DD` and is ≤ current `schedule.startDate`. If equal → no-op alert "Same as current start date." If greater → reject with alert "To trim forward use END TODAY or REMOVE."
2. New start date ≥ 2020-01-01 and ≤ today (reasonable bounds).
3. New start weight is a positive finite number.
4. If schedule was removed in another tab between modal open + apply, abort with alert.

### Apply logic (the only code path that writes)

```js
function applyEditStartDate() {
  const sched = gs(SK.schedule);
  if (!sched) { closeEditStartDate(); return; }

  const newStartStr = document.getElementById('esdDate').value;
  const newStartWeight = parseFloat(document.getElementById('esdWeight').value);

  // ... validation (see above) ...

  // Auto-backup before write — same pattern as requiresBackup migrations
  if (typeof downloadJson === 'function') {
    const snapshot = {};
    Object.values(SK).forEach(k => { snapshot[k] = gs(k); });
    downloadJson(`protocol-health-pre-startdate-edit-${todayStr()}.json`, snapshot);
  }

  // Rebuild days[] from newStartStr through the last existing day
  const lastDay = (sched.days && sched.days.length)
    ? sched.days[sched.days.length - 1]
    : sched.startDate;
  const newDays = [];
  const cur = strToDate(newStartStr);
  const end = strToDate(lastDay);
  while (cur <= end) {
    newDays.push(dateToStr(cur));
    cur.setDate(cur.getDate() + 1);
  }

  sched.startDate    = newStartStr;
  sched.startWeight  = newStartWeight;
  sched.days         = newDays;
  sched.totalDays    = newDays.length;
  sched.exactDays    = newDays.length; // mirror — exactDays is the unreduced total
  ss(SK.schedule, sched);

  // Mirror to settings so getSettings().startDate stays consistent
  const s = getSettings();
  s.startDate = newStartStr;
  saveSettings(s);

  dispatch('SCHEDULE_ADJUSTED'); // existing event — refreshes calendar, durationBar, radar, export
  closeEditStartDate();
  closeManageSchedule();
  showAlert('START DATE UPDATED', 'Schedule extended backward to ' + newStartStr + '. A backup was downloaded before the change.');
  setTimeout(() => renderCalendar(), 50);
}
```

### What we deliberately do NOT do

- ❌ Touch `SK.fastDays` / `SK.lightDays` (user's recorded fast/light history stays as-is)
- ❌ Run `autoSetPlanFastDays()` / `autoSetPlanLightDays()` on the backfilled range (avoids duplicating user choices)
- ❌ Call `calcAdjust()` (no re-estimation of target date)
- ❌ Touch `SK.weights` / `SK.dayLogs` / `SK.foodLog` / `SK.activityHistory` (no data mutation outside schedule + settings)
- ❌ Bump schema version (no shape change)
- ❌ Add a new SK key
- ❌ Modify any plans/* or migrations/* file

## Safety / Risk

| Risk | Mitigation |
|---|---|
| User picks a start date that has no weight log → start weight unknown | Auto-fill from nearest available weight (search backward from selected date, fallback to oldest weight in log). Field stays editable. |
| User accidentally extends start to wrong date | Auto-backup JSON is downloaded before write. User can RESTORE from this backup if needed. |
| Settings.startDate desync from schedule.startDate | Plan explicitly mirrors both fields. |
| Future ADJUST after edit produces stale math | `calcAdjust` reads the fresh values; math will be correct because elapsed = (today - newStartDate) and rate = (curW - newStartWeight) / elapsed. |
| User picks a date later than current startDate | Hard reject with alert pointing to END TODAY / REMOVE. |
| Two open tabs race on schedule edit | `gs(SK.schedule)` is re-read at apply time; if `null`, abort. Last-writer-wins for the field updates (acceptable for a manual recovery tool). |
| Calibration / radar reads inconsistent intermediate state | All field writes happen in a single `ss(SK.schedule, sched)` call. Atomic from localStorage's perspective. |
